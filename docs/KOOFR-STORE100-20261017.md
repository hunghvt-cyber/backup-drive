## Audit and schema

Read maina09b63b2c520312a70c8e13b645537f62fb7711a from GitHub and compared the
Notes/share/validation APIs with local source (only trailing whitespace differed).
Current Note fields: id,title,text,checklist[{id,text,checked}],pinned,folder,
updatedAt,history(max5),deleted; opaque revision for conditional updates. Individual
share links edit Note content, preserve pinned/folder; folder links permit listing,
reading, creating and editing only within the folder. Shared-folder deletion is
blocked until folder links are revoked. Revoked link renewal generates a new token.
No expiry is added. Production auth remains its existing shared-password session.

The prototype preserves logical fields/semantics but changes storage internals:
- One immutable JSON file per Note revision; no full-store content rewrite per save.
- catalog.json is the single commit point: current file/hash, folder membership,
  deleted flag, content summary, revision counter, folders and hashed capabilities.
- Logical revision includes a random store epoch + per-Note metadata revision.
  Moves/deletes invalidate old drafts; a restored new store has a new epoch.
- Full content/checklist/history is NOT duplicated into the catalog. Preview text
  is100 characters. This is not a full-text-search implementation.
- Every shared read and mutation locks only the NEW synthetic root collection,
  Depth:infinity,60s; every revision/catalog PUT carries the inherited token.
  Root lock serializes catalog/ACL publication, including revocation. Expired
  writers cannot publish after another owner commits a revoke. In-flight reads
  already authorized before revocation cannot be retracted from the network.
- Save: acquire root lock, read live catalog/current revision, validate capability
  and base, write new immutable file, verify it, publish/verify catalog, unlock.
  A failed publish leaves an orphan ignored by all reads. Exact op retries reuse
  the orphan even if their new timestamp differs. No blind unconditional overwrite.
-24 recent catalog receipts bind operation ID to request hash/actor. Revoked-token
  auth is checked BEFORE replay; eviction falls back to base-revision conflict.
- Folder moves and deletion/unfiling are atomic metadata publications. Deleted
  Notes are tombstones; no physical data DELETE is implemented or tested here.

Tradeoff: global collection lock serializes reads/writes, and full safe saves have
more HTTP calls than the earlier5-call single-note primitive. The previous0.97s
measurement is NOT a benchmark for this full prototype. Keep-like UX, busy retries,
large-note support, public HTTP session/CSRF integration and iPad drafts remain gates.
Fixture record ceiling is28KB serialized value /32KB read, smaller than production's
1MB content +3MB record limits; do not call this a drop-in replacement.

## Test plan

39 simulations pass. Live Vercel stages are separately bounded (function120s):
1. Create a new root/catalog;10 chunks of10 immutable Notes; verify all100 full
   bodies, IDs, Unicode/checklists/pinned flags and four folder memberships.
2. Owner CRUD, conditional conflict, same-op retry, duplicate checklist rejection,
   soft-delete/no resurrection, empty-folder and two folder-deletion policies.
3. History cap5; live note edit/view share, denied escalation/cross-note access,
   revoke-before-replay authorization and new-token renewal.
4. Folder workspace creation/edit scope, outside-note and move-out denial,
   live move-back membership, delete guard, revoke and renewal.
5. Same-base concurrency; pause a shared writer past5s lease, revoke under new
   root lock, then reject its old token on member PUT and catalog publication.
   Its already-written orphan must never become the Note HEAD.
6. Durable snapshot of104 stored records (100 active +4 tombstones), folders,
   checklists/history and capability metadata. Restore to a separate fresh store,
   block normal reads while incomplete, inject a lost catalog publish in chunk3,
   resume without duplicate files, verify104 records and100 active Notes.
   Reset store epoch and revoke ALL restored links; reject old links/revisions.

The control plane is an OIDC-authenticated fixture route, not public Homepage share
URLs. Owner/capability operations run through the same prototype service over real
Koofr storage; no UI/iPad/browser/public-link end-to-end claim. Raw test link tokens
may be returned once to the private Actions harness for restore checks; the runner
must keep them in memory and strip them before reports/logs/artifacts. No Koofr
password, Google credential, raw capability, body or lock token is logged.

Snapshots are integrity-checked against accidental corruption, not cryptographically
authenticated against a malicious storage account. Backup and restore are on the
same provider; independent export/retention/account-loss DR remains unverified.
Immutable orphan/history garbage collection is intentionally not implemented.
